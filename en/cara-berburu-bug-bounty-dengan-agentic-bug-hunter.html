How to Hunt Bug Bounties with Agentic-Bug-Hunter (Free, Local AI)

Agentic-Bug-Hunter is an open-source toolkit for bug bounty: from recon to reporting, everything is AI-assisted and runs from the terminal. The interesting part: it can run completely free with a local AI model via Ollama — no paid API key needed. I have tried the pipeline myself on a local demo target, and this tutorial summarizes its commands and how to use them.

Figure 1: The bug bounty hunting workflow — from scope to report.

Warning: Only hunt targets that are in scope for an official bug bounty program (HackerOne, Bugcrowd, Intigriti, Immunefi). Read the program's policy first before touching any asset. Never scan a site you don't own or that has no bug bounty program.

What You Need



- Python 3.11+ and Git.
- Ollama + a local AI model (for example qwen2.5:3b) — free, no API key.
- Recon tools (subfinder, httpx, katana, nuclei) — most of them come installed with the repo.

Part 1: Installation and Setup



Step 1: Clone the repo and enter its virtual environment.
git clone https://github.com/awarexone/Agentic-Bug-Hunter
cd Agentic-Bug-Hunter

Step 2: Set the provider and model. This command saves your choice in the config — run it once at the start. What I use: Ollama + qwen2.5:3b (local, free).
bughunter setup --provider ollama --model qwen2.5:3b

Step 3: Check the status. This command shows the active provider and model, the target currently being worked on, and how far along the progress is.
bughunter status
Tip: If Ollama disappears after a restart (its binary got deleted), just reinstall the binary — the models you already downloaded are safe in the Ollama model folder, no need to download them again.

Part 2: Commands



The CLI has 12 main commands. They all run through bughunter — the global flags --provider, --model, and --no-banner work with every command.
Basic commands. providers lists all providers with their status (which one is active, which one has no API key yet). models lists the models available for the active provider. chat opens an interactive AI shell — handy for asking questions about a target or discussing findings without running the full pipeline.
recon <target> — recon and attack surface analysis. Runs the full recon pipeline, then AI analyzes the attack surface: subdomain enumeration, live host checks, URL collection, parameter discovery, then a nuclei scan. Results are saved in the recon/<target>/ folder.
bughunter recon target.com

hunt <target> — the full pipeline. The main command: recon, vulnerability hunting, validation, and reporting, in a single run. The --quick option runs fewer checks — faster, good for a first pass.
bughunter hunt target.com
bughunter hunt target.com --quick

validate [finding] — the 7-Question Gate. Tests a single finding with seven questions (is there a PoC, is the impact concrete, would a triager consider it a real bug, is it in scope, and so on). The result: KEEP (worth reporting) or DROP (discard). Run this for every finding BEFORE writing the report — invalid reports hurt your validity ratio on the platform.
bughunter validate "robots.txt membocorkan /admin dan /.env"

triage [finding] — quick triage. A quick alias for validate: a brief assessment of one finding, without the full gate. Use it when there are many candidate findings and you want to filter which ones deserve a full validation.
report — write a submission-ready report. Writes a bug report ready to submit to a platform (HackerOne/Bugcrowd/Intigriti/Immunefi format, complete with CVSS). This command takes no target argument — it reads the existing findings folder. Always read the draft first before submitting; the decision to submit is yours, not the tool's.
bughunter report
bughunter report --findings-dir findings/target.com

chain [finding] — chain exploits A → B → C. Takes one finding and chains exploits together — for example XSS, steal a token, then take over an account. A chain like this has a far bigger impact than a single bug on its own, and is usually paid more.
bughunter chain "XSS di halaman profil"

mcp — MCP server, doctor, and the tool catalog. Three subcommands: serve runs the MCP server so other AIs can use the bug hunter tools; doctor checks the health of the MCP setup; tools shows the catalog of tools available via MCP.
bughunter mcp serve
bughunter mcp doctor
bughunter mcp tools

Part 3: The Full Workflow



Step 1: Scope. Make sure the program and its assets are in scope — read the program policy first.
Step 2: Recon. Map the target's attack surface.
Step 3: Hunt. Look for vulnerabilities in that attack surface.
Step 4: Validate every finding with the 7-Question Gate — discard the weak ones.
Step 5: Write the report and read the draft before submitting.
bughunter recon target.com
bughunter hunt target.com
bughunter validate "temuan pertama"
bughunter report

Limits You Should Know



- Raw IP:port targets (for example 127.0.0.1:8080) can't be scanned by the standard pipeline — recon treats the target as not a live host, so the scan silently never runs. The workaround: fill in a manual URL list, then run the scanner directly.
- The CLI only covers 7 families of checks: upload, SQLi, XSS, SSTI, CMS, MFA, SAML. Not tested: SSRF, open redirect, auth bypass, /.env exposure, CORS, LFI, IDOR, JWT, GraphQL — those live in the plugin's slash commands, not the CLI.
- Local models are slow: qwen2.5:3b runs at about 5.7 tokens/second after tuning — a 2000-token analysis takes about 6 minutes. This model also sometimes hallucinates endpoints from junk Wayback URLs — verify every quoted URL before acting on it.
- Nuclei needs TMPDIR outside /tmp — /tmp is only a 512 MB tmpfs, while the nuclei templates are about 83 MB.
- The repo's built-in demo target is already hardened — a correct scan produces zero findings. Use it only as a smoke test.
